### Finding 1 (Critical) — `UpdateUserRoleServlet` has no server-side self-modification guard

`manage_roles.jsp` tells the operator "The logged-in Super Admin cannot change their own role or inactive status from this page, preventing accidental lockout" ([manage_roles.jsp:582-585](src/main/webapp/manage_roles.jsp:582)) and enforces this **only** by hiding the edit form for the caller's own row (`isCurrentUser` at [manage_roles.jsp:458,492](src/main/webapp/manage_roles.jsp:458)). Reading `UpdateUserRoleServlet.doPost()` in full (lines 20-198) shows **no comparison of `targetUserId` to the caller's own `user_id` anywhere** — `manage_roles.jsp`'s own error-message table even has a dedicated `"self".equals(error)` branch ready to render ("You cannot change your own role or status from this page.", [manage_roles.jsp:295-298](src/main/webapp/manage_roles.jsp:295)), but **no code path in the servlet ever sets `error=self`** — the branch is unreachable dead code, strong evidence the server-side check was planned/intended but never implemented. **This is a "UI works, backend unprotected" finding**: an ADMIN (or SUPER_ADMIN, who can also call this endpoint per its role check) can bypass the UI entirely and `POST /UpdateUserRoleServlet` with their own `userId`, changing their own `current_role` or setting their own `status=INACTIVE` — self-locking themselves out with no UI safeguard in the way.

### Finding 2 (Critical) — Super-Admin protection in `UpdateUserRoleServlet` is keyed on a literal username, not on role

[UpdateUserRoleServlet.java:105](src/main/java/com/mycompany/asset_management_system_ams/UpdateUserRoleServlet.java:105) protects the Super Admin account with `if ("super_admin".equalsIgnoreCase(targetUsername))` — comparing the **target's username string** to the literal `"super_admin"`, not the target's actual `current_role`/`oldRole` (which the code already fetched into `oldRole` at line 93, but never checks against `"super_admin"` for this purpose). The only place `oldRole` is checked is `if ("admin".equals(oldRole) && !"admin".equals(newRole))` ([UpdateUserRoleServlet.java:117](src/main/java/com/mycompany/asset_management_system_ams/UpdateUserRoleServlet.java:117)), which protects the **Admin** role, not Super Admin. **Consequence**: if the real Super Admin account's username is ever anything other than the literal string `super_admin` (e.g. renamed, or a second Super Admin account created with a different username — nothing in the schema prevents multiple `current_role='super_admin'` rows), an ADMIN can silently change that account's `current_role` to anything (including `employee`) via a normal POST, with **no error, full success, and a `role_assignment_log` row that looks like a routine role change** — this is a real privilege-sabotage / denial-of-service path against the highest-privileged account in the system. The existing test [RoleDutyAssignmentSecurityTest.testUpdateUserRoleServlet_DenyModifyingSuperAdminAccount](src/test/java/com/mycompany/asset_management_system_ams/RoleDutyAssignmentSecurityTest.java:84) does not catch this because its mock happens to use the username `"super_admin"` for both the target's username *and* implicitly assumes that's how the real account is named — it validates the happy path where the fragile assumption holds, not the case where it doesn't.

### Finding 3 (High) — The same username-based "protected account" pattern recurs throughout `RoleAssignmentDAO`

`RoleAssignmentDAO.PROTECTED_ACCOUNTS = Arrays.asList("super_admin", "admin", "assetmgr", "depthead", "auditor", "employee")` ([RoleAssignmentDAO.java:18](src/main/java/com/mycompany/asset_management_system_ams/RoleAssignmentDAO.java:18)) is a hardcoded list of **expected seed usernames**, used to mean "this is one of the six built-in system accounts, don't touch it via the dynamic-duty workflow." It's consumed by:
- `resolveEffectiveRoleForUser()` ([RoleAssignmentDAO.java:782-788](src/main/java/com/mycompany/asset_management_system_ams/RoleAssignmentDAO.java:782)) — the function that decides a logged-in user's **effective session role on every login** (called from `LoginServlet.java:187`). For any of the six literal usernames it trusts `loggedRole` (the DB's `current_role`) as-is; for everyone else it looks up dynamic duty assignments instead.
- `isAssignmentForProtected()` ([RoleAssignmentDAO.java:763-775](src/main/java/com/mycompany/asset_management_system_ams/RoleAssignmentDAO.java:763)) — blocks deactivating a dynamic assignment belonging to one of those literal usernames.
- `assignRoleToEmployee()`'s ADMIN-uniqueness step ([RoleAssignmentDAO.java:192-201](src/main/java/com/mycompany/asset_management_system_ams/RoleAssignmentDAO.java:192)) and `getActiveAssignments()`/`getAssignableEmployeesForDropdown()` — all filter "real" system accounts by `username NOT IN ('super_admin','admin','assetmgr','depthead','auditor','employee')`.

This is a **systemic design choice, not an isolated bug**: role protection app-wide is convention-based (assume the six seed accounts always keep these exact usernames) rather than data-driven (check `current_role` or a dedicated `is_system_account` flag). It happens to be internally consistent — the same six literal strings are used everywhere — but it is fragile by construction: it silently stops protecting the real privileged accounts the moment any of those usernames are renamed, or the moment an organization legitimately creates a second Admin/Auditor/etc. account with a different username (which the schema fully permits — `current_role` is just an enum column, nothing ties "is protected" to it). Confirmed this isn't hypothetical: [seed_data.sql:23](seed_data.sql:23) and [super_admin_setup.sql:8-19](src/main/resources/migrations/super_admin_setup.sql:8) are the only places usernames `admin`/`super_admin` actually get created, and nothing in the schema or application enforces that these specific usernames must exist or must stay mapped to their respective roles going forward.

### Finding 4 (Critical, credential hygiene) — Default Super Admin password committed to source control in plaintext

[src/main/resources/migrations/super_admin_setup.sql:8-19](src/main/resources/migrations/super_admin_setup.sql:8) creates the `super_admin` account with `'super_admin123'` written directly into the `password_plaintext` column **as literal cleartext in a file checked into this repository**, alongside its precomputed BCrypt hash. [seed_data.sql:23](seed_data.sql:23) does the same for the legacy `admin`/`admin123` account. Anyone with read access to this repository (including, per the Phase-0 inventory, the previously-noted leaked Gmail credential in `WEB-INF/notification.properties`) has the default Super Admin password for any deployment that runs this migration without immediately rotating it. Neither script sets `force_password_change=1` for the account it creates (`super_admin_setup.sql` copies whatever value the source `admin` row already had, defaulting to whatever `admin` was left at). **This is a real, low-effort account-takeover path for any environment that runs the provided setup scripts as-is** — flagging as P0 alongside the equivalent `emp001123`-style predictable-password finding from Module 1.

## 3. Business Workflow / Lifecycle Check

Two parallel, intentionally-separate role mechanisms exist, and the boundary between them is a real design decision worth documenting explicitly (not itself a defect):

1. **Permanent role** (`users.current_role`) — changed only via `manage_roles.jsp`/`UpdateUserRoleServlet`, gated to ADMIN/SUPER_ADMIN. This is what `LoginServlet` falls back to if dynamic-duty resolution fails ([LoginServlet.java:197](src/main/java/com/mycompany/asset_management_system_ams/LoginServlet.java:197)).
2. **Dynamic duty** (`employee_role_assignments`) — a temporary elevation layered on top, changed via `role_assignment.jsp`/`RoleAssignmentServlet`, gated to ADMIN/DEPARTMENT_HEAD (**not** SUPER_ADMIN — the JSP explicitly redirects SUPER_ADMIN away with `?error=unauthorized`, [role_assignment.jsp:28-31](src/main/webapp/role_assignment.jsp:28), and the servlet enforces the identical restriction, [RoleAssignmentServlet.java:25](src/main/java/com/mycompany/asset_management_system_ams/RoleAssignmentServlet.java:25) — consistent across both layers, so this reads as deliberate: Super Admin manages permanent roles only, Admin/Dept-Head manage day-to-day duty coverage).

`RoleAssignmentDAO.resolveEffectiveRoleForUser()` (called at every login, [LoginServlet.java:187](src/main/java/com/mycompany/asset_management_system_ams/LoginServlet.java:187)) merges the two: for the six protected accounts it trusts `current_role` outright; for everyone else it computes an effective role from active `employee_role_assignments` rows with a fixed priority order `ADMIN > ASSET_MANAGER > DEPARTMENT_HEAD > AUDITOR > EMPLOYEE` ([RoleAssignmentDAO.java:806](src/main/java/com/mycompany/asset_management_system_ams/RoleAssignmentDAO.java:806)), falling back to `EMPLOYEE` if none exist. The DAO's own code comments document at least one previously-fixed real bug in this exact resolution path (stale `user_id` snapshot causing a real Asset Manager to silently log in as a plain Employee, [RoleAssignmentDAO.java:106-121](src/main/java/com/mycompany/asset_management_system_ams/RoleAssignmentDAO.java:106)) — the class of bug (a duty assignment silently failing to resolve and defaulting to the lowest-privilege role) is now guarded against for the specific stale-`user_id` cause that was found, but the pattern itself (silent fallback to `EMPLOYEE` on any lookup failure, e.g. a DB error swallowed by the DAO's try/catch) means a real elevated-duty user could be silently under-privileged (fails safe, not open — acceptable direction to fail, but worth monitoring for support-ticket noise).

`assignRoleToEmployee()` cascades correctly through several real side-effects on a single transaction: deactivating the target's prior active duty, deactivating a superseded ADMIN duty elsewhere, updating `employees.designation`, and re-syncing `departments.department_head_user_id` for both the newly-assigned and any previously-vacated department ([RoleAssignmentDAO.java:149-295](src/main/java/com/mycompany/asset_management_system_ams/RoleAssignmentDAO.java:149)) — this is genuinely well-engineered multi-table consistency, not a superficial single-row update.

## 5. Status Model Check

- `users.current_role` is a 6-value enum (`super_admin, admin, asset_manager, auditor, dept_head, employee`) — no state-machine transition rules beyond the handful of ad-hoc guards in `UpdateUserRoleServlet` (can't assign super_admin; can't demote the sitting admin except via the auto-reassignment path). No impossible states found in the enum itself (a user is always exactly one role).
- `employee_role_assignments.assignment_status` is `ACTIVE`/`INACTIVE` — correctly enforced as effectively single-active-per-employee by `assignRoleToEmployee()`'s step 1.8, which deactivates any existing active duty before inserting a new one ([RoleAssignmentDAO.java:216-223](src/main/java/com/mycompany/asset_management_system_ams/RoleAssignmentDAO.java:216)) — this prevents the "two simultaneous active elevated duties for one employee" impossible state the methodology specifically calls out to check for. Good.
- **Possible impossible state**: nothing found that prevents `users.current_role` (permanent) and the employee's active `employee_role_assignments.role_code` (dynamic) from disagreeing indefinitely — e.g. an employee's dynamic duty says `ASSET_MANAGER` while their permanent `current_role` still says `employee`. This is by design (that's the whole point of the dynamic layer), but it does mean two different admin screens (`manage_roles.jsp` showing permanent role vs. `role_assignment.jsp`/`access_matrix.jsp` implying effective role) can legitimately show different answers to "what role does this person have?" for the same user — a UX/comprehension risk worth a P2 recommendation (a combined "effective role" indicator) rather than a defect.

## 6. RBAC & Security Check

- **CSRF**: same app-wide absence as Module 1 — no tokens on any form here either. `B1` (Change Role) has no re-authentication requirement (unlike Module 1's Change-Password/Emergency-Reset), making it a **clean CSRF target**: a logged-in ADMIN visiting a malicious page could have their session silently used to change another user's role with zero additional secret required. Combined with Finding 1/2 above, this is a compounding risk — CSRF could be used to drive the self-modification and username-spoofing gaps without the admin's knowledge.
- **RBAC enforcement**: genuinely double-layered for page access (`RoleAuthorizationFilter`/`RoleAccessUtil` + each JSP/servlet's own inline check) — consistent with Module 1's finding. `RoleAssignmentServlet`'s DEPARTMENT_HEAD scoping is real server-side enforcement (`EmployeeDAO.isEmployeeUnderDepartmentHead()`), not a UI filter — confirmed by the dedicated passing test `testRoleAssignmentServlet_IDOR_DenyDepartmentHeadOutsideDept` ([RoleDutyAssignmentSecurityTest.java:51](src/test/java/com/mycompany/asset_management_system_ams/RoleDutyAssignmentSecurityTest.java:51)).
- **IDOR**: `B4`'s DEPARTMENT_HEAD path re-derives the target employee from the `assignment_id` server-side and re-checks department ownership ([RoleAssignmentServlet.java:121-137](src/main/java/com/mycompany/asset_management_system_ams/RoleAssignmentServlet.java:121)) rather than trusting anything from the client about department — correct pattern, no IDOR found here.
- **Self-escalation via `RoleAssignmentServlet`**: explicitly blocked twice over — `SUPER_ADMIN` role can never be assigned dynamically ([RoleAssignmentServlet.java:57](src/main/java/com/mycompany/asset_management_system_ams/RoleAssignmentServlet.java:57) and independently re-checked in the DAO, [RoleAssignmentDAO.java:154](src/main/java/com/mycompany/asset_management_system_ams/RoleAssignmentDAO.java:154)) — belt-and-braces, good. Covered by `RoleAccessUtilTest.testSelfEscalationBypassBlocked`.
- **Finding 1/2/3/4 above** are the dominant security findings for this module — see detailed writeups.

## 7. Audit Log & Data Integrity Check

- Both role-change surfaces write to `audit_logs` via the shared `AuditDAO.log()` helper, consistent with the rest of the app. Permanent role changes additionally write structured `role_assignment_log` rows (old role → new role, who, when, `is_emergency` flag) — a stronger audit shape than the free-text `audit_logs.action_details` alone, and specifically useful for after-the-fact review of privilege changes.
- Not immutable at the DB layer (same finding as Module 1 — no triggers/append-only constraints on either `audit_logs` or `role_assignment_log`).
- Dynamic-duty cascading side-effects (auto-deactivating a superseded ADMIN duty, department-head column resync) each get their own audit row rather than being silently folded into the primary action's log entry — good granularity for reconstructing what actually happened during a complex reassignment.

## 8. Missing Features / Gaps

- No notification to the affected user (or to a demoted prior admin) when their role changes — they discover it only by noticing different menu options on next login.
- No approval workflow for permanent role changes — a single ADMIN can unilaterally promote/demote any non-protected user, no second-approver/four-eyes control for an action this sensitive (may be an acceptable design choice for a system this size, but worth calling out).
- No visible "effective role" reconciliation view showing permanent role vs. active dynamic duty side by side for a given user (§5).
- No time-boxed/expiring dynamic duty assignment in the UI despite the schema supporting it (`effective_to DATE NULL` exists on `employee_role_assignments`, [schema.sql:924](schema.sql:924)) — `assignRoleToEmployee()` never sets `effective_to` on insert (only on deactivation, as an end-marker), so every dynamic assignment is open-ended until someone manually deactivates it; no "assign this duty for 2 weeks while X is on leave" workflow exists even though the column is there for it.
- No self-service "who has what role" export/report distinct from `access_matrix.jsp` (which documents the *policy*, not the *current assignment state*) — cross-check against Module 24 (Reports) once audited.

## 9. Advanced Feature Recommendations

- **P0** — Add a server-side self-modification guard to `UpdateUserRoleServlet` (compare `targetUserId == adminUserId`, wire up the already-designed `?error=self` path).
- **P0** — Replace username-literal "protected account" checks (`UpdateUserRoleServlet.java:105`, `RoleAssignmentDAO.PROTECTED_ACCOUNTS` and all its call sites) with a check against `current_role = 'super_admin'` (and, for the broader protected set, an explicit `is_system_account` flag or role-based check) so protection travels with the role, not a guessed username.
- **P0** — Remove plaintext default passwords from `seed_data.sql`/`super_admin_setup.sql` (generate a random password at setup time and print/require immediate rotation, or at minimum force `force_password_change=1` unconditionally on the created account) and rotate any already-deployed default credentials.
- **P0** — CSRF tokens on `UpdateUserRoleServlet`/`RoleAssignmentServlet` specifically, given the compounding risk with Findings 1–2.
- **P1** — Notify the affected user (and any auto-demoted prior admin) by email/in-app notice when their role changes.
- **P1** — Reconcile/retire `seed_data.sql`'s stale two-role scheme so it can't be run against a fresh install by mistake and silently diverge from the real 6-role/`super_admin_setup.sql` path.
- **P2** — Time-boxed dynamic duty assignments (use the existing `effective_to` column) with an automated expiry sweep.
- **P2** — Combined "effective role" view per user (permanent + active dynamic duty) on `manage_roles.jsp`.
- **P3** — Two-person approval for permanent role changes to ADMIN/SUPER_ADMIN-adjacent roles.

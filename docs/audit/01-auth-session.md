**Scope:** Login, Logout, Forgot Password, Reset Password (+ account activation), Change Password, Emergency Admin Recovery, Generate Employee Login.
**Verification layers used:** (a) static code reading — full. (b) live UI click-through — **not performed this pass** (no dev server/DB was started in this session; see §10 for manual steps). (c) direct backend/API call — **not performed this pass**. All statuses below are therefore capped at `CODE LOOKS CORRECT — NEEDS RUNTIME VERIFICATION` even where the code is well-hardened; nothing here is marked `VERIFIED WORKING` per the methodology's requirement of UI+API confirmation.

## 3. Business Workflow / Lifecycle Check

Auth isn't part of the physical asset lifecycle, but it gates every other module's lifecycle actions and has its own mini-lifecycle:

- **New employee → login provisioning**: `Employees` module creates the employee record; **Auth module (A7)** provisions the `users` row on demand (not automatic) — an admin/asset-manager/super-admin must explicitly click "Generate Login". Reversible (no login can be deleted from this module — no "revoke access" control was found here; likely lives in Employees/RBAC module, to confirm there).
- **Forced first login → password change**: `force_password_change=1` is set on generation ([GenerateEmployeeLoginServlet.java:106](src/main/java/com/mycompany/asset_management_system_ams/GenerateEmployeeLoginServlet.java:106)) and on the reset branch ([GenerateEmployeeLoginServlet.java:106](src/main/java/com/mycompany/asset_management_system_ams/GenerateEmployeeLoginServlet.java:106)), enforced at login ([LoginServlet.java:200-235](src/main/java/com/mycompany/asset_management_system_ams/LoginServlet.java:200)) by redirecting to `change_password.jsp` regardless of what page was requested. Cannot be bypassed by directly navigating elsewhere in this module's code (would need to check whether `RoleAuthorizationFilter`/other JSPs also check this session flag — flag for RBAC module).
- **Emergency admin handoff**: single-step, immediately effective, transactional, fully auditable, but **irreversible via UI** — un-doing an emergency handoff requires a second emergency-reset run (no "undo" or approval workflow); acceptable for a break-glass procedure but worth documenting as intentional.
- **Password reset / activation**: both single-use, time-boxed (30 min), correctly invalidate prior outstanding tokens of the same type on a new request ([PasswordResetDAO.java:160](src/main/java/com/mycompany/asset_management_system_ams/PasswordResetDAO.java:160)).

## 5. Status Model Check

- `users.status`: `ACTIVE` / `INACTIVE` only ([schema.sql:809](schema.sql:809)). Login query explicitly filters `AND status = 'ACTIVE'` ([LoginServlet.java:84](src/main/java/com/mycompany/asset_management_system_ams/LoginServlet.java:84)) so an `INACTIVE` account cannot authenticate — correctly enforced at the DB query level, not just a UI check. No `LOCKED`/`SUSPENDED` distinct status — the brute-force lockout (§2/A1) is a **derived, time-windowed** state computed from `login_security_attempts` rows, not a persisted status column; this means a locked-out account looks identical to a normal `ACTIVE` account everywhere else in the system (admin screens, reports) — an admin has no way to see "this account is currently locked" without querying `login_security_attempts` directly. Worth a P1 recommendation (§9) to surface this.
- `users.force_password_change`: boolean, correctly gates the post-login redirect ([LoginServlet.java:234](src/main/java/com/mycompany/asset_management_system_ams/LoginServlet.java:234)) and is cleared on both self-service change ([ChangePasswordServlet.java:77](src/main/java/com/mycompany/asset_management_system_ams/ChangePasswordServlet.java:77)) and reset-via-email ([ResetPasswordServlet.java:95](src/main/java/com/mycompany/asset_management_system_ams/ResetPasswordServlet.java:95)). No impossible-state risk found here — it's a single independent flag, not a state machine.
- `password_reset_tokens` (current/self-healed shape) has three real states: unused-unexpired (valid), `used_at` set (spent), expired (`expires_at` passed) — all three are checked together in `resolveValidToken` ([PasswordResetDAO.java:219-260](src/main/java/com/mycompany/asset_management_system_ams/PasswordResetDAO.java:219)), so a used-and-expired token can't be replayed. Correctly enforced server-side, not just via the JSP's read-only pre-check.

## 6. RBAC & Security Check

| Concern | Finding |
|---|---|
| **CSRF** | **Confirmed app-wide: zero CSRF protection exists anywhere in this codebase** (`grep -rli "csrf" src/main/java src/main/webapp` → 0 hits). Every POST form in this module (`login.jsp`, `change_password.jsp`, `emergency_recovery.jsp`) submits with no anti-CSRF token, and `RoleAuthorizationFilter`/`RoleAccessUtil` only check session role, not request origin. **Mitigating factor specific to this module**: the two most sensitive state-changing actions here (Change Password, Emergency Admin Recovery) both require the acting user's *own current password* in the POST body ([ChangePasswordServlet.java:69](src/main/java/com/mycompany/asset_management_system_ams/ChangePasswordServlet.java:69), [EmergencyAdminResetServlet.java:83](src/main/java/com/mycompany/asset_management_system_ams/EmergencyAdminResetServlet.java:83)) — a blind cross-site POST can't supply a value the attacker doesn't know, so classic silent-CSRF doesn't apply to those two specifically. It **does** apply to Logout (low impact) and to `GenerateEmployeeLoginServlet` (A7/A8, no password re-entry) — a malicious page visited by a logged-in Admin/Asset-Manager/Super-Admin could silently trigger login generation or password resets for an arbitrary `employeeId` via a cross-site auto-submitting form/fetch, since the browser attaches the session cookie automatically. **This is a real, exploitable CSRF gap on A7/A8 and should be scored accordingly (see §11).** |
| **Session cookie hardening** | `web.xml` sets only `<session-timeout>30</session-timeout>` ([web.xml:14-16](src/main/webapp/WEB-INF/web.xml:14)) — no `<cookie-config>` block, so `HttpOnly`/`Secure`/`SameSite` are left to container/Tomcat defaults rather than explicitly pinned. `SecurityHeadersFilter` was checked and sets no cookie attributes either. Recommend explicitly setting `Secure` (HTTPS-only) and `SameSite=Lax` or `Strict` at minimum, which would also close most of the CSRF gap above for GET-based actions. |
| **RBAC enforcement** | Consistently double-layered: `RoleAuthorizationFilter` (global `/*` servlet filter, [RoleAuthorizationFilter.java:15](src/main/java/com/mycompany/asset_management_system_ams/RoleAuthorizationFilter.java:15)) + `RoleAccessUtil.hasAccess()` default-deny map, **plus** each sensitive servlet in this module re-checks role/identity itself (`EmergencyAdminResetServlet.java:37`, `GenerateEmployeeLoginServlet.java:32`) rather than trusting the filter alone — good defense-in-depth, not frontend-only anywhere in this module. |
| **IDOR** | `EmergencyAdminResetServlet` takes a raw `targetUserId` int with no ownership scoping beyond role-checks on the target's *current* role (can't target an existing admin/super-admin) — appropriate, since this endpoint's whole purpose is to act on an arbitrary other user, gated purely by the *caller's* privilege (SUPER_ADMIN), which is correctly re-verified server-side. `GenerateEmployeeLoginServlet` takes a raw `employeeId` with no department/ownership scoping — for the roles allowed to call it (SUPER_ADMIN/ADMIN/ASSET_MANAGER, all global-scope roles per RoleAccessUtil), this is consistent with the rest of the app's design, not an IDOR beyond what the role already grants. |
| **Password strength policy** | Minimum length **6 characters**, no complexity requirement (upper/lower/digit/symbol), no check against common-password lists, no max-length cap seen (`ChangePasswordServlet.java:47`, `ResetPasswordServlet.java:57`) — weak by current standards (NIST 800-63B would accept a low complexity bar but expects ≥8 chars and breach-list checking). |
| **Predictable temp passwords** | `GenerateEmployeeLoginServlet`'s generated password is always `username + "123"` ([GenerateEmployeeLoginServlet.java:98,146](src/main/java/com/mycompany/asset_management_system_ams/GenerateEmployeeLoginServlet.java:98)) — this is a fixed, guessable formula. Anyone who can see or guess an employee's username (visible on ID badges, QR labels, employee lists to multiple roles per RoleAccessUtil, or predictable from `employee_code`) can compute their password without ever needing the admin to disclose it, **entirely bypassing the `force_password_change=1` flag's practical protection** (an attacker who logs in first, before the real employee, can be prompted to change the password themselves and lock the legitimate user out). | **BCrypt cost factor** | `BCrypt.gensalt()` with no explicit cost/rounds argument ([PasswordUtil.java:29](src/main/java/com/mycompany/asset_management_system_ams/PasswordUtil.java:29)) — uses jBCrypt's default (10 rounds), acceptable but worth confirming intentional vs. an oversight; not itself a finding, just noted. |

## 7. Audit Log & Data Integrity Check

- Every mutating action in this module writes to `audit_logs` via the shared `AuditDAO.log()` helper ([AuditDAO.java:10](src/main/java/com/mycompany/asset_management_system_ams/AuditDAO.java:10)), which also auto-populates `ip_address`/`user_agent` from `RequestContext` (bound per-request by `SecurityHeadersFilter`) — consistent, not ad-hoc per servlet.
- **Not immutable at the DB layer**: `audit_logs` has no trigger, no append-only constraint, and the application connects with a single DB user that (as far as this module's code shows) has ordinary `UPDATE`/`DELETE` privileges on it — nothing stops a compromised admin session or a future buggy servlet from altering/deleting rows. This is a data-integrity gap common to the whole app, not unique to Auth, but Auth is where it matters most (login/lockout/password-reset history is exactly the evidence you'd want tamper-resistant during an incident investigation).
- `action_details` is a single free-text field ([schema.sql:356](schema.sql:356)), not structured old-value/new-value columns — acceptable for narrative events like `LOGIN`/`LOGOUT`, but for `PASSWORD_RESET_COMPLETED`/emergency role changes a structured before/after would be stronger for compliance review than parsing prose.
- `role_assignment_log` (used by `EmergencyAdminResetServlet`) *does* capture structured `old_role`/`new_role` — better model than `audit_logs` for that one action; worth applying the same pattern more broadly (flagged in §9).
- Login failure classification (`WRONG_PASSWORD` vs `UNKNOWN_USERNAME` vs `INACTIVE_USER_LOGIN_ATTEMPT`) depends on `getLoginFailureDetails()`'s `JOIN roles r ON u.role_id = r.role_id` ([LoginServlet.java:585-593](src/main/java/com/mycompany/asset_management_system_ams/LoginServlet.java:585)) — **this hits the same `role_id` schema-drift bug from §4**. If `role_id` doesn't exist on the live `users` table, this query throws, is swallowed by the surrounding try/catch, and every failed-login audit/alert for a *known* username silently misclassifies as `UNKNOWN_USERNAME` (the pre-set default, [LoginServlet.java:572](src/main/java/com/mycompany/asset_management_system_ams/LoginServlet.java:572)) instead of `WRONG_PASSWORD` — meaning a real security team reviewing login-failure audit logs post-incident would see "unknown username" spam for what were actually password-guessing attempts against real accounts, materially degrading incident-response quality. This needs the same schema verification called out in §4 before it can be ruled in or out.

## 8. Missing Features / Gaps

- **No MFA/2FA** anywhere in the schema or code (no `mfa_secret`, TOTP, or SMS/email OTP path) — for a system managing organizational assets/finances this is a notable gap for privileged roles (SUPER_ADMIN/ADMIN) at minimum.
- **No account-lockout visibility for admins** — the derived lockout state (§5) isn't surfaced on any admin screen in this module; an admin can't proactively see or manually clear a lockout.
- **No "revoke/deactivate login" action in this module** — generation and password-reset exist, but no symmetric "disable this user's login" was found here (may exist in Employees/RBAC module — flag to check there and cross-reference).
- **No session-list / "active sessions" view** — a user (or admin) can't see or remotely terminate other active sessions for an account; relevant for the emergency-recovery scenario itself (after demoting an admin, their existing session isn't force-invalidated by `EmergencyAdminResetServlet` — they stay logged in with old-role session data until it naturally expires or they hit an authorization check that re-resolves role, which — per `RoleAssignmentDAO.resolveEffectiveRoleForUser` being called only at login — likely means **a demoted admin keeps their old-privilege session live** until they log out or the session times out. This is a real operational gap in the emergency-recovery workflow's completeness: demoting an admin who is mid-session doesn't actually revoke their live access immediately.**
- **No password history / reuse prevention** beyond "can't equal current password" (`ChangePasswordServlet.java:52`) — a user can cycle between two passwords indefinitely.
- **No self-registration/sign-up entry point found** in this module despite `ResetPasswordServlet`'s doc comment describing an activation flow ("Sign up") — worth confirming in Employees module whether account creation always originates from an admin action (A7) rather than employee self-service; if so the "Sign up" framing in the code comment is stale/misleading.

## 9. Advanced Feature Recommendations

- **P0** — Resolve the `users.role_id` schema-drift finding (§4/§7): reconcile `schema.sql` with the live schema (or vice-versa), and add a startup/deploy-time schema-verification check so this class of drift is caught before go-live, not discovered via silently-swallowed exceptions in production.
- **P0** — Replace the deterministic `username+"123"` temp password (§6) with a cryptographically random one-time password, delivered only through the admin's screen (as today) and never guessable from public information.
- **P0** — Add CSRF tokens to all state-changing POST endpoints, starting with `GenerateEmployeeLoginServlet` (A7/A8) which has no other mitigation.
- **P1** — Force-invalidate the demoted admin's live session(s) as part of `EmergencyAdminResetServlet`'s transaction (e.g. a `session_version` counter on `users`, checked per-request) so an emergency handoff takes effect immediately, not just for future logins.
- **P1** — Surface account-lockout state on an admin-facing screen with a manual "clear lockout" action.
- **P1** — Explicit `<cookie-config>` (`Secure`, `HttpOnly`, `SameSite=Lax`) in `web.xml`.
- **P1** — MFA/TOTP for SUPER_ADMIN and ADMIN roles at minimum.
- **P2** — Password history (reject last N), complexity policy, breach-list check (e.g. HaveIBeenPwned k-anonymity API) on change/reset.
- **P2** — Structured old-value/new-value columns on `audit_logs` (or a supplementary table) instead of free-text `action_details`, at least for identity/role/financial-value changes.
- **P3** — Self-service "my active sessions" view with remote sign-out, once session tracking beyond the container default exists.

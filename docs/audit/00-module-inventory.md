# AMS Production-Readiness Audit — Module Inventory (Phase 0)

**Audited repo:** `Asset_Management_System_AMS` ("Railway AMS — East Coast Railway Asset Management System")
**Stack:** Jakarta EE 10 (Servlet 6.0 + JSP/JSTL, no framework like Spring), MySQL (via `mysql-connector-j`, raw JDBC — no ORM), Maven/WAR packaging, deployed to a servlet container (Tomcat, per WAR name `RailwayAMS`). Frontend is server-rendered JSP + vanilla JS (`src/main/webapp/js/*.js`) + hand-written CSS — no SPA framework.
**Auth:** Custom session-based auth (`LoginServlet`), custom RBAC via `RoleAccessUtil` (in-memory `ROLE_MAP`, checked by `RoleAuthorizationFilter`, a `/*` servlet filter) — not a standard framework like Spring Security.
**Notable:** No ORM — all SQL is hand-written JDBC in `*DAO.java` classes. `schema.sql` (56KB) is the source of truth for ~42 tables; `migrations/` has only one incremental file (`001_physical_verification_updates.sql`) despite `schema.sql` referencing many more evolved features, meaning schema drift between fresh-install and evolved-install paths is a real risk to check per-module.
**Prior work found:** `CHANGELOG-fixes.md` (5325 lines) documents a prior autonomous audit-fix pass, at minimum on the Login/Forgot-Password module, including critical fixes (dead `force_password_change` enforcement, plaintext password writes, session fixation, account lockout) and an explicitly **unrotated leaked Gmail credential** in `WEB-INF/notification.properties`. This audit re-verifies current-state code, not the changelog's claims, but the changelog is useful cross-reference context — link findings back to it where relevant instead of re-discovering already-documented issues from scratch.
**Test suite:** `src/test/java/.../*Test.java` — 13 files (JUnit 5 + Mockito): `AdminHandoffTest`, `AssetDAOTest`, `CopilotContextUnderstandingTest`, `CopilotRegressionTest`, `CopilotToolCatalogSecurityTest`, `DBSeederTest`, `DashboardDAOTest`, `DepartmentModuleSecurityTest`, `EmployeeModuleSecurityTest`, `LoginServletIntegrationTest`, `PasswordUtilTest`, `RoleAccessUtilTest`, `RoleDutyAssignmentSecurityTest`. JSPs are not covered by any automated test (Jasper-compiled at runtime only) — noted per-module.
**No dedicated migrations for most schema evolution** — `schema.sql` appears hand-maintained as a single file rather than migrated incrementally; this itself is a Phase-1 finding to raise under the module(s) it affects most (Settings/System Admin, DB integrity).

Root directory also contains ~30 ad-hoc one-off `.java`/`.class` utility scripts (`FixCSSImages`, `CleanLogic`, `HashGen`, `InsertSuperAdmin`, `UpdatePasswords`, etc.), compiled `.class` files, a `maven.zip`, and a bundled `apache-maven-3.9.9/` — these are dev/ops scratch tools, not part of the deployed WAR, but their presence in the repo root (some directly manipulating passwords/schema) is itself a hygiene/security-hygiene finding to raise in the final report.

## Audit Plan / Sequencing

Given 28 modules at the full 11-section depth this prompt specifies (each requiring UI→handler→API→controller→validation→DB tracing with file:line citations), this is a multi-session effort. Proposed sequencing, grouped by criticality and dependency order (foundation modules first, since later modules' RBAC/audit-log sections depend on how those primitives actually behave):

1. Auth & Session
2. RBAC / Roles & Permissions
3. Audit Logs (needed as a reference point before judging "is X audited?" in every other module)
4. Asset Registry
5. Asset Allocation/Assignment
6. Asset Requests
7. ... remaining modules in criticality order (Physical Verification, QR, Employees, Maintenance, Returns, Disposal, Warranty, Departments, Categories, Vendors, Category-Vendor Mapping, Transfer, Maintenance Requests, Profile Change Requests, Document Vault, Notifications, Settings/System Admin, Reports/Exports, Dashboard, Global Search, AI Copilot, Tunnel Control)

This file will be updated if module boundaries need revision as Phase 1 uncovers shared/duplicated logic.
